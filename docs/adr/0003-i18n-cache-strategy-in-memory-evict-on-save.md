# ADR-0003: 다국어 캐시 전략 - 인메모리, 저장 시점 즉시 갱신

- 상태: Accepted
- 날짜: 2026-09-15

## 컨텍스트

DB 기반 메시지 조회는 요청마다 DB를 직접 조회하면 성능 부담이 크다. 캐싱
전략과, 관리자가 메시지를 수정했을 때 캐시를 어떻게 최신 상태로 유지할지를
정해야 한다. 검토한 대안:

캐시 저장소:
1. 애플리케이션 인메모리(단일 인스턴스 내 `ConcurrentHashMap`)
2. Redis 공유 캐시(다중 인스턴스 간 공유)
3. 캐시 없음(매 조회마다 DB 직접 조회)

갱신 트리거:
- 수동 reload API
- 주기적 TTL 재조회
- 저장(쓰기) 시점에 해당 엔트리만 즉시 갱신

## 결정

**인메모리 캐시(대안 1) + 저장 시점 즉시 갱신을 사용한다.**

- 앱 기동 시 `KKDUGI_I18N_MSG` 전체를 인메모리 맵으로 적재한다.
- `MessageAdminService`가 INSERT/UPDATE/DELETE에 성공하면, 그 직후 해당
  `(msgCd, langCd)` 키만 DB에서 다시 읽어 캐시 맵을 갱신한다(삭제된 경우
  맵에서 제거). 전체 재적재(full reload)는 하지 않는다.
- 별도의 수동 reload API나 TTL 기반 폴링은 두지 않는다.

## 근거

- 현재 단일 인스턴스로 운영되므로 Redis 공유 캐시(대안 2)의 복잡도(무효화
  전파, 직렬화)가 아직 필요하지 않다. 다중 인스턴스 확장 시 재검토한다.
- 캐시 없음(대안 3)은 구현은 가장 단순하지만, 메시지 조회가 요청마다
  DB를 타게 되어 요청 경로 성능에 직접 영향을 준다.
- 저장 시점 즉시 갱신은 관리자 화면에서 메시지를 수정한 직후 조회 결과가
  바로 바뀌어야 한다는 요구를 만족하면서도, 전체 리로드보다 비용이 훨씬
  적다.

## 결과

- 캐시 무효화 로직이 `MessageAdminService`의 쓰기 경로에 결합된다. DB를
  우회해 직접 데이터를 조작(수동 SQL 등)하면 캐시가 갱신되지 않으므로,
  운영 데이터 변경은 반드시 애플리케이션 경로를 통해야 한다.
- 다중 인스턴스로 확장할 경우, 인스턴스별 캐시가 서로 어긋날 수 있다. 이
  시점에는 Redis 기반 무효화 전파(pub/sub 등)를 재검토해야 한다.

## 보강 (2026-09-15, ADR-0007과 함께 결정)

관리 CRUD API가 여러 행을 한 트랜잭션으로 처리하는 배치 저장으로 확정되면서
([ADR-0007](0007-admin-crud-single-endpoint-batch-save.md)), "저장 시점 즉시
갱신"의 의미를 다음과 같이 명확히 한다:

- 캐시 갱신은 DB 쓰기 도중이 아니라 **트랜잭션이 실제로 커밋된 뒤**
  (`TransactionSynchronization.afterCommit`)에만 수행한다.
- 이유: 배치 내 다른 행 처리가 실패해 트랜잭션 전체가 롤백되는 경우, 커밋
  전에 캐시를 먼저 바꿔버리면 캐시가 실제로 반영되지 않은 DB 상태를 가리키게
  된다. 커밋 후 갱신은 이 불일치를 원천적으로 막는다.
- 이 결정은 본 ADR의 결론(인메모리 캐시, 저장 시점 즉시 갱신)을 뒤집지 않고
  구현 시점을 구체화한 것이다.

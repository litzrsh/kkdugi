# API 요청 메뉴 컨텍스트 적용

2026-09-19

## 목적

후속 SercurityChecker Aspect가 요청을 발생시킨 메뉴를 판별하도록 로그인·로그아웃을 제외한 API에 X-Menu-Id를 전달한다. 계약은 [요청 컨텍스트](../../api/request-context.md)를 따른다.

## 구현

- 공통 HTTP 계층에서 메뉴 ID 유효성 및 필수 여부를 검증하고 헤더를 추가한다.
- API의 forMenu(menuId)는 생성 시 메뉴 ID를 고정한다. PageHost는 메뉴별로 재생성되며 해당 객체를 자식 페이지에 주입한다.
- 코드·메시지·메뉴 목록/저장과 팝업 콜백은 기존 API 호출 형태를 유지하면서 요청 메뉴 ID를 전달한다.
- Pragma 요청은 대상 메뉴 ID를 명시한다. 메뉴 선택 전 트리 조회는 사용자가 승인한 예약 값 __shell__을 사용한다.
- 로그인 vanilla JS 요청과 로그아웃 요청에는 헤더를 추가하지 않는다.
- SercurityChecker 및 보안 annotation/config/pom의 기존 작업은 보존한다. 실제 서버 인가 구현은 후속 범위다.

## 검증 범위

- 실제 메뉴 ID 전달, 본문 보존, 일반/공통 API, 로그인·로그아웃 제외.
- 메뉴 변경 중 이전 화면 및 팝업 콜백 컨텍스트, Pragma 대상 일치.
- 누락/잘못된 ID의 전송 차단, shell 값의 사용 범위 제한.
- JavaScript 계약 테스트, Maven 테스트, 데스크톱·모바일 fixture 화면의 실제 요청 헤더 확인.

## 검증 결과

- JavaScript: 35개 통과.
- Maven: 149개 통과.
- 실제 Spring 렌더링 Pragma와 정적 Vue 자원을 사용하는 브라우저 fixture: 데스크톱·모바일 통과, API/Pragma 요청 25건의 메뉴 ID 확인. 실패 응답(404/409)과 재시도도 포함한다.
- 기존 인증 테스트에서 SYS_ADMIN을 중복 생성해 고유 제약에 걸리는 문제가 확인되어, 해당 두 테스트가 기본 시드 권한을 참조하도록 fixture를 보정했다. 업무 코드 및 기본 권한 데이터는 변경하지 않았다.
- 서버의 Aspect 인가 차단은 이번 검증 범위에 포함하지 않는다.

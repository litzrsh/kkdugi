# 배치 시스템 설계 초안

- 작성일: 2026-09-20
- 상태: 검토용 초안. 기능·논리 테이블 설계이며 API 계약, DDL, 구현은 아직 확정하지 않는다.
- 확정 요구: admin은 `kkdugi-admin`에 구현, runner는 머신에 별도 설치, 등록 프로그램으로 Job 생성, 자동·수동 실행 지원.
- 확정 요구: **Job 하나는 프로그램 하나를 실행한다.** 향후 여러 Job을 연결하는 Workflow로 확장할 수 있어야 한다.
- 확정 요구: **Workflow의 진행 여부는 admin이 결정한다.** Runner의 Job 완료 이벤트를 받은 admin이 다음 단계를 자동 진행하거나 Workflow owner의 승인을 기다린다.
- 그 외 아래 정책과 수치는 제안이며 구현 전에 조정할 수 있다.

## 1. 구성과 책임

| 구성 | 책임 |
| --- | --- |
| Admin (`kkdugi-admin`) | Runner·프로그램·Job·스케줄 관리, 실행 요청과 배정, 상태·로그·감사 이력, 사용자 권한 검사. 향후 Workflow 진행 판단·owner 승인 대기·승인 후 재개 |
| Runner (별도 프로젝트) | 머신 서비스로 실행, 프로그램 설치 정보 보고, 작업 수신, 프로세스 실행·종료, 생존 신호와 결과·로그 전송 |
| PostgreSQL | 설정, 실행 큐, 배정 소유권, 실행 이력의 영속 저장 |
| 실행 프로그램 | 실제 업무 처리. Java JAR, Python, OS 실행 파일 등 runner에 사전 설치한 프로그램 |

Runner가 HTTPS로 admin에 작업을 요청하는 **pull 방식**을 제안한다. 머신으로 들어오는 별도 연결 없이 등록·조회·결과 보고를 수행한다. GitLab Runner도 서버에 작업을 요청하는 polling/long polling 방식을 사용한다. 여기서는 통신 방향을 참고하며 GitLab 프로토콜과의 호환성을 목표로 하지는 않는다. [GitLab 공식 문서](https://docs.gitlab.com/ci/runners/long_polling/)

초기에는 짧은 polling + 실패 시 backoff/jitter를 사용하고, 규모가 커지면 long polling을 검토한다. 큐의 원장은 PostgreSQL로 두고 Redis·메시지 브로커를 필수 의존성으로 추가하지 않는다. Admin의 스케줄러는 실행 요청만 만들며 업무 프로그램을 직접 실행하지 않는다.

## 2. 핵심 개념

| 개념 | 의미 | 예시 |
| --- | --- | --- |
| Runner | 설치된 실행 에이전트 한 개 | `batch-worker-01` |
| Program | 업무 프로그램의 논리적 정의와 입력 규격 | `daily-sales` |
| RunnerProgram | 특정 runner에 설치된 프로그램과 버전·경로 | worker-01의 `/opt/batch/sales.jar`, 버전 `1.2` |
| Job | Program 하나 + 기본 입력 + 실행 대상 + 실행 정책 | 전일 매출 집계 |
| Schedule | Job의 자동 실행 시각과 시간대 | 매일 02:00, `Asia/Seoul` |
| Run | 자동·수동 요청 한 번에 대한 실행 이력 | 9월 20일 전일 매출 집계 요청 |
| Attempt | Run을 실제로 수행하는 시도 한 번 | 첫 시도 실패, 두 번째 시도 성공 |

하나의 프로그램으로 입력이 다른 여러 Job을 만든다. 하나의 Job에는 스케줄을 0개 이상 연결한다. 스케줄이 없어도 수동 실행할 수 있다. 같은 논리 프로그램을 여러 runner에 설치할 수 있으므로 Program과 설치 정보를 분리한다.

**Job 설정, Run, Attempt를 분리하는 것이 Workflow 확장의 기반이다.** Job 설정을 수정해도 과거 실행 내용은 바뀌지 않고, Workflow는 기존 Run 생성 기능을 호출해서 각 단계를 실행한다. [확장 설계](workflow-extension.md)

예를 들어 `Job1 → Job2 → Job3`에서 Job1 완료를 admin이 확정한 뒤, Job2의 진입 정책에 따라 바로 실행 요청을 만들거나 owner 승인 대기로 전환한다. Owner가 승인하면 admin이 Job2를 요청한다. Runner는 현재 Job의 실행 결과만 보고하며 다음 Job을 선택하거나 연쇄 실행하지 않는다.

## 3. 필요한 기능

| 영역 | 1차 범위 | 주요 정책 |
| --- | --- | --- |
| Runner 관리 | 사전 등록, 일회성 등록 자격증명, 인증키 발급·폐기, 연결 상태, 일시 중지, 동시 실행 수 | 사용 여부와 온라인 상태를 분리, 중지는 새 배정만 차단 |
| 프로그램 관리 | 프로그램 정의, 입력 규격, runner별 설치 등록·승인·사용 중지 | 실행 파일 배포·업데이트는 별도 운영 작업 |
| Job 관리 | 생성·변경·비활성화, 기본 입력, 대상 runner, timeout, 재시도, 중복 실행 정책 | Job 하나 = Program 하나 |
| 스케줄 관리 | cron, 시간대, 활성화, 다음 실행 시각, 누락 실행 처리 | Job당 여러 스케줄, admin 재시작 후 복구 |
| 수동 실행 | 입력 재정의, 즉시 요청, 실행 요청 중복 방지, 과거 실행 재실행 | cron을 경유하지 않고 같은 실행 큐에 등록 |
| 실행 제어 | 대기·배정·시작·완료, 취소, timeout, 실패 재시도 | 취소 요청과 실제 프로세스 종료를 구분 |
| 모니터링 | 실행 목록·상세, 시도별 종료 코드·로그·사유, runner 생존 상태 | 결과 불명 상태를 실패로 단정하지 않음 |
| 감사·권한 | 조회, 설정 관리, 실행, 취소, runner 자격증명 관리 | 기존 admin 인증·권한 체계에 연결 |
| 보관 관리 | 로그 용량 제한, 보관 기간별 정리 | 실행 요약보다 로그를 먼저 정리 |

1차 실행 대상은 **runner 직접 지정**을 제안한다. 테이블에는 논리 프로그램과 설치 관계를 구분해두므로 나중에 runner pool/태그 기반 배정도 추가할 수 있다. 동일 프로그램이 다른 머신에 있다는 이유만으로 장애 시 자동 이동시키지는 않는다.

## 4. 프로그램 등록 흐름

1. 관리자가 admin에 runner를 생성하고 짧은 유효기간의 일회성 등록 토큰을 발급한다.
2. 머신에 runner를 설치하고 admin 주소·등록 토큰으로 연결한다. 이후 runner 전용 인증키를 사용한다.
3. 관리자가 admin에 논리 프로그램 코드, 이름, 입력 스키마를 만든다.
4. 머신 운영자가 실행 파일을 배포하고 runner 설정에 프로그램 코드, 실행 파일·고정 인자·작업 디렉터리·버전을 등록한다.
5. Runner가 설치 정보를 admin에 보고한다. 관리자가 해당 설치를 승인하면 Job에서 사용할 수 있다. 실행 정의나 버전이 바뀌면 새 revision으로 재승인한다.
6. 관리자가 승인된 프로그램·runner를 선택해 Job을 만들고 필요하면 스케줄을 연결한다.

예: runner에는 `java` 실행 파일과 고정 인자 `-jar /opt/batch/sales.jar`를 등록한다. Job에는 `businessDate` 같은 업무 입력만 등록한다. Runner가 선언된 규칙에 따라 입력을 인자 배열로 변환하며, 임의의 shell 명령 문자열을 admin에서 전달하지 않는다. 스크립트는 승인된 interpreter와 script 경로를 고정해서 실행한다.

입력은 Job 기본값에 수동 실행·스케줄의 값을 덮어쓴 후 검증한다. 일자 표현식이 필요하면 `scheduledAt`, 시간대 등 제한된 실행 컨텍스트만 지원하고 일반 스크립트 평가를 허용하지 않는다. 표현식을 해석한 최종 값은 Run에 저장하며 재시도에서 다시 계산하지 않는다. 비밀 값은 머신의 secret 참조로 관리한다.

## 5. 초기 정책 제안

| 항목 | 기본 제안 |
| --- | --- |
| 실행 성공 | 종료 코드 0. 다른 코드는 실패. 예외적인 성공 코드는 프로그램별 확장 가능 |
| Job 중복 실행 | `QUEUE`: 같은 Job은 한 번에 하나, 다음 요청은 대기 |
| 큐 대기 제한 | Job별 대기 timeout과 대기 개수 상한 설정, 초과는 명시적 사유와 함께 거절/만료 |
| Runner 동시 실행 | 기본 1, 승인된 capacity 내에서 설정 |
| 프로그램 동시 실행 | 같은 runner의 같은 프로그램도 기본 1; 다른 Job이 같은 프로그램을 호출하는 경우 포함 |
| 실행 timeout | Job마다 명시, 예시 1시간. 배정 대기 시간과 별도 |
| 자동 재시도 | 기본 0회. 종료가 확인된 재시도 가능 실패에만 횟수·간격 설정 |
| 결과 불명 | 자동 재실행 금지, 프로세스/업무 상태 확인 후 운영자 판단 |
| 스케줄 누락 | `SKIP` 기본. 복구 시 지나간 구간 요약을 감사 이력에 기록 |
| 시간 | 실행 시각은 UTC instant, 스케줄에는 IANA 시간대 저장 |
| 로그 | 초기 DB chunk 보관, 예시 시도당 10 MiB·30일. 초과·유실 여부 표시 |

cron은 초를 포함한 6필드 형식으로 고정하는 안을 제안한다. 저장 전에 유효성과 다음 실행 시각을 검증한다. DST로 없는 현지 시각은 건너뛰고, 중복 현지 시각은 두 UTC 시각을 별개 발생으로 취급하는 정책을 명시한다. 실제 cron 라이브러리는 이 정책을 만족하는지 구현 시 검증한다.

## 6. 단계별 범위

1. **실행 기반:** runner 인증·프로그램 등록·Job CRUD·수동 실행·Run/Attempt·로그·취소·timeout·장애 복구.
2. **자동 배치:** 영속 스케줄·중복 생성 방지·누락 처리·실패 재시도·보관 정리. 1~2단계까지가 최초 요구사항의 완성 범위다.
3. **운영 확장:** runner pool/태그, 알림, 대용량 로그·산출물 저장소, 운영 통계.
4. **Workflow:** admin이 담당하는 Job 연결·진행 판단, 자동 진행/owner 승인, 승인 대기·재개, 의존성·병렬 실행·조건 분기, 단계별 입력/결과 매핑, Workflow 실행·승인 이력.

초기 제외: 프런트엔드 구현, 프로그램 원격 배포, 컨테이너 executor, 머신 자동 증설, 조직 관리, Workflow 엔진 구현. Runner 구현 언어·지원 OS·설치 형식은 별도 결정한다. 설계는 OS별 프로세스 트리 종료와 서비스 재시작 복구가 가능해야 한다는 요구만 둔다.
